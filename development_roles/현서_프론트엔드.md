# 현서 역할 — Google AI Studio Android 프론트엔드

작성일: 2026-10-13  
담당자 성격: 개발 경험이 거의 없으며 AI 도구 중심으로 작업  
목표: Kotlin·Jetpack Compose Android 화면을 만들고 Spring Boot REST API와 안정적으로 연결

## 1. 최종 책임

현서는 사용자가 직접 접하는 Android 앱의 화면과 사용 흐름을 책임진다. Google AI Studio로 초안을 빠르게 만들되, 생성된 결과를 그대로 완료로 보지 않고 실제 기기에서 빌드·실행·입력·오류 상태를 확인한다.

### 반드시 책임질 영역

- 화면 목록과 사용자 이동 흐름 구현
- Kotlin·Jetpack Compose UI
- Material 3 기반 일관된 디자인
- 입력 폼과 기본 형식 검증
- Mock 데이터로 화면 선완성
- Spring Boot REST API 호출
- 로그인 상태와 토큰 사용
- 로딩·빈 결과·오류·재시도 상태
- 이미지 선택과 업로드 요청
- 접근성·가독성·다양한 화면 크기 점검
- 실제 Android 기기 또는 에뮬레이터 테스트
- 오류 재현 절차와 테스트 결과 기록

- 입력값이 비어 있는지 확인

- 사용자의 확인이 필요한 다이얼로그
- 이미지 선택과 미리보기
- 앱에서 표시할 날짜와 숫자 형식

### 성준과 합의 후 구현할 것

- 로그인 토큰 저장과 갱신

- DB 테이블과 컬럼
- 사용자 권한과 접근 규칙

## 3. 화면별 상세 업무

### 3.1 로그인·초기 설정

- 스플래시 화면
- 로그인 및 회원가입 화면
- 비밀번호 표시·숨김
- 입력 오류 안내
- 프로필 입력
- 필수 동의와 선택 동의 구분
- 로그인 만료 시 재로그인 안내

완료 기준:

- 키보드가 입력창이나 버튼을 가리지 않는다.
- 서버 오류와 필드 오류가 구분되어 표시된다.
- 로그인 중 중복 탭으로 요청이 여러 번 발생하지 않는다.

### 3.2 홈 대시보드

- 오늘 날짜와 간단한 인사
- 오늘의 습관 진행 상태
- 예정 식사 또는 최근 식사
- 다음 복약 일정
- 빠른 기록 버튼
- 데이터가 없을 때 시작 안내

완료 기준:

- 화면 하나의 API가 실패해도 전체 앱이 종료되지 않는다.
- 사용자가 다음 행동으로 이동할 수 있는 버튼이 명확하다.

### 3.3 습관

- 오늘의 습관 목록
- 완료·미루기·건너뛰기 버튼
- 습관 등록·수정 폼
- 요일과 시간 선택
- 진행 상태 표시
- 처리 중 버튼 중복 입력 방지
- 성공 후 목록 새로고침

완료 기준:

- 서버가 반환한 회차 상태를 그대로 표시한다.
- 완료 후 재알림이 중단되었는지는 서버 결과를 기준으로 보여준다.

### 3.4 식사

- 아침·점심·저녁·간식·야식 선택
- 실제 식사 시각 입력
- 여러 음식 추가·삭제
- 섭취량과 단위 입력
- 탄수화물·단백질·지방·당·카페인·칼로리 표시
- 직접 등록 음식 입력
- 식사 사진 선택·미리보기·삭제
- 기록 완료·건너뜀·미완료 표시
- 일간·주간 영양 합계 화면

완료 기준:

- 숫자 필드는 잘못된 문자와 음수를 방지한다.
- 영양 합계는 최종적으로 서버 응답을 기준으로 표시한다.
- 사진 권한 거부와 업로드 실패를 처리한다.

### 3.5 의약품 사전 — 우선순위 1

- 검색창과 최근 검색어
- 검색 로딩 상태
- 검색 결과 목록
- 결과 없음 상태
- 약 이름·업체명·제형 등 요약 표시
- 의약품 상세 화면
- 효능·사용법·주의사항·부작용·보관법·제형·모양 표시
- 정보 출처와 갱신일 표시
- 개인 복약으로 등록 버튼

완료 기준:

- 검색 중 입력이 바뀔 때 불필요한 요청을 줄인다.
- 짧은 시간에 여러 검색 응답이 도착해도 최신 결과를 표시한다.
- 상세 정보가 없는 항목은 빈 공간이 아니라 `정보 없음`으로 표시한다.
- 의약품 정보가 진단이나 처방을 대신하지 않는다는 안내를 표시한다.

### 3.6 개인 복약

- 복약 목록과 상태
- 처방약·일반의약품·영양제·운동 보충제 구분
- 복용 목적·기간·회당 복용량 입력
- 요일과 시간 설정
- 식전·식후·공복 선택
- 복용·건너뜀 등 실제 행동 입력
- 실제 복용 시각 입력
- 중지·종료 확인

완료 기준:

- 복약 시각 계산을 앱에서 임의로 하지 않고 서버의 예정 시각을 표시한다.
- 같은 회차의 버튼을 여러 번 눌러도 중복 요청이 발생하지 않도록 처리한다.

### 3.7 통계와 설정

- 오늘의 습관 완료율
- 일간·주간 영양 합계
- 복약 이행률
- 기간 선택
- 알림 설정 화면
- 로그아웃 및 기본 프로필 수정

MVP에서는 복잡한 차트보다 숫자, 진행률, 단순 막대 그래프를 우선한다.

## 4. Google AI Studio 사용 절차

### 1단계 — 한 화면씩 생성

앱 전체를 한 번에 요청하지 말고 기능별로 생성한다.

프롬프트 예시:

```text
Kotlin과 Jetpack Compose, Material 3로 한국어 Android 화면을 만들어줘.
화면 이름은 의약품 사전 검색이다.
검색창, 로딩, 검색 결과 목록, 결과 없음, 오류와 재시도 상태가 필요하다.
각 결과에는 약 이름, 업체명, 제형을 표시하고 선택하면 상세 화면으로 이동한다.
현재는 Repository가 반환하는 Mock 데이터만 사용한다.
MVVM 구조를 유지하고 API 키나 의료 판단 로직을 넣지 마라.
```

### 2단계 — 생성 결과 확인

- 프로젝트가 빌드되는가?
- 앱이 실행되는가?
- 뒤로 가기가 정상인가?
- 빈 화면과 오류 화면이 있는가?
- 긴 한국어 텍스트가 잘리지 않는가?
- 같은 컴포넌트가 중복 생성되지 않았는가?

### 3단계 — Mock 데이터 연결

성준이 제공한 실제 응답 예시와 동일한 Kotlin 데이터 클래스를 만든다. 화면은 Mock Repository를 통해 이 데이터를 사용한다.

### 4단계 — 실제 API로 교체

- API 인터페이스 추가
- Repository에서 API 호출
- ViewModel에서 로딩·성공·오류 상태 관리
- 화면은 상태를 관찰하고 표시
- URL과 필드명은 임의로 바꾸지 않음

### 5단계 — 실제 기기 검증

에뮬레이터만으로 완료 처리하지 않는다. 실제 Android 기기에서 네트워크, 카메라·사진 권한, 키보드, 화면 크기, 알림 권한을 확인한다.

## 5. 권장 앱 코드 구조

```text
app/
  core/
    network/       공통 API 클라이언트
    model/         공통 모델
    ui/            공통 색상·글꼴·컴포넌트
  feature/
    auth/
    home/
    habit/
    meal/
    medication/
    drugdictionary/
    statistics/
    settings/
```

각 기능 폴더는 가능한 한 다음 구조를 유지한다.

```text
feature/drugdictionary/
  data/            API·Repository
  model/           화면에서 사용하는 모델
  ui/              Screen·Component
  viewmodel/       화면 상태와 사용자 이벤트
```

AI가 모든 코드를 한 파일에 만들면 기능별 파일로 나누도록 다시 요청한다.

## 6. 성준에게 요청해야 할 자료

API 연동 전에 다음 자료가 없으면 추측해서 구현하지 말고 요청한다.

- API 주소와 메서드
- 요청·응답 JSON
- 필수 필드와 선택 필드
- 상태값 목록
- 오류 코드와 의미
- 날짜·시간 예시
- 테스트 계정
- 개발 서버 주소
- 사진 업로드 예제
- 인증 토큰 사용 방법

오류를 전달할 때는 `안 돼요` 대신 다음 형식으로 전달한다.

```text
기능: 의약품 검색
실행 환경: Android 에뮬레이터 / 앱 버전
재현 절차: 검색창에 타이레놀 입력 → 검색 버튼 선택
예상 결과: 검색 결과 목록 표시
실제 결과: 오류 화면 표시
HTTP 상태: 400
응답 내용: ...
관련 로그: ...
재현 횟수: 3회 중 3회
```

비밀번호, 전체 토큰, 개인정보는 오류 보고에 포함하지 않는다.

## 8. 매일 확인할 체크리스트

- 오늘 작업한 화면이 빌드되고 실행되는가?
- Mock과 실제 API 모델이 계약과 일치하는가?
- 로딩·빈 결과·오류 상태가 모두 있는가?
- 버튼을 연속으로 눌러도 중복 요청이 발생하지 않는가?
- 서버 오류가 사용자에게 이해 가능한 문장으로 표시되는가?
- 긴 글과 작은 화면에서도 UI가 깨지지 않는가?
- 비밀번호·토큰·API 키가 코드나 로그에 없는가?
- 변경 내용을 작은 단위로 커밋했는가?

## 9. 현서가 하지 말아야 할 일

- AI가 만든 전체 프로젝트를 검토 없이 덮어쓰지 않는다.
- 빌드 오류를 해결하려고 라이브러리 버전을 무작정 변경하지 않는다.
- JSON 필드가 마음에 들지 않는다는 이유로 임의로 이름을 바꾸지 않는다.
- 프론트엔드에서 복약 판단이나 권한 검사를 대신 구현하지 않는다.
- API 키와 서버 비밀번호를 코드에 입력하지 않는다.
- 한 번에 여러 기능을 생성한 뒤 무엇이 깨졌는지 모르는 상태를 만들지 않는다.
- 화면이 보인다는 이유만으로 실제 API 연동 완료라고 판단하지 않는다.

## 10. 최종 인수 조건

- 새 환경에서 Android 프로젝트가 빌드된다.
- 실행 방법과 필요한 환경설정이 문서화되어 있다.
- 모든 핵심 화면에 로딩·빈 결과·오류 상태가 존재한다.
- 실제 서버로 공동 시연 시나리오가 동작한다.
- 화면별 테스트 결과와 알려진 제한사항이 정리되어 있다.
- 앱 코드에 API 키·DB 비밀번호·실제 사용자 데이터가 없다.
- APK 또는 내부 테스트용 빌드를 재생성할 수 있다.
