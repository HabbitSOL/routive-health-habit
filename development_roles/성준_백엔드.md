# 성준 역할 — Spring Boot 백엔드

작성일: 2026-10-13  
담당자 성격: Java 개발 가능, 전체 기술 구조 책임  
목표: Android 앱이 사용할 안정적인 REST API와 MariaDB 기반 업무 시스템 완성

## 1. 최종 책임

성준은 프로젝트의 기술 기준과 데이터 일관성을 책임진다. 화면이 요청한 데이터를 단순히 저장하는 역할을 넘어 인증, 권한, 일정 계산, 중복 방지, 알림 조건, 식사와 복약 연계 같은 핵심 업무 규칙을 서버에서 구현한다.

### 반드시 책임질 영역

- Spring Boot 프로젝트 구조
- MariaDB 스키마와 마이그레이션
- 인증·인가 및 사용자별 데이터 격리
- 공통 API 응답과 예외 처리
- 습관·식사·복약·의약품 사전 API
- 일정 회차 생성과 상태 변경 규칙
- 최초 알림과 제한된 재알림 처리
- 식사 완료 시각 기반 식후 복약 시각 계산
- 이미지 업로드의 서버 정책과 메타데이터 저장
- 분석 이벤트 수신
- 단위·통합·권한 테스트
- 실행 환경과 배포
- 현서의 API 연동 지원 및 최종 코드 검토

## 2. 시작 전에 확정할 기술 기준

### 프로젝트 기본값

- Java 21 LTS
- Spring Boot 4.0.8
- Maven Wrapper
- MariaDB 11.4 LTS
- Flyway 마이그레이션
- Spring Security
- Spring Data JPA 사용, 복잡한 조회는 명시적 JPQL 또는 SQL 사용
- JUnit 기반 단위·컨텍스트 테스트, DB 통합 테스트는 Testcontainers 도입 예정
- 개발·테스트·시연 환경 설정 분리

선정일: 2026-10-14. 공식 Spring Initializr에서 생성 가능한 안정판을 기준으로 하며, 업그레이드는 시연 안정화 이후 별도 작업으로 처리한다.

### API 공통 규격

- 기본 경로: 예시 `/api/v1`
- 인증 헤더: 예시 `Authorization: Bearer {token}`
- 시간 형식: ISO 8601, 시간대 포함
- 목록 응답: 페이지 번호·크기·전체 개수 형식
- 공통 오류: 코드, 메시지, 필드 오류, 추적 ID
- 멱등성 키 적용 범위
- 파일 업로드 크기와 허용 형식

현서가 화면을 만들기 전에 최소한 로그인, 의약품 검색, 습관 목록, 식사 등록, 복약 등록의 요청·응답 예제를 제공한다.

## 3. 기능별 상세 업무

### 3.1 회원과 인증

- 이메일 중복 확인과 정규화
- 비밀번호 해시 저장
- 회원가입·로그인·로그아웃
- 액세스 토큰과 갱신 정책
- 사용자 프로필 조회·수정
- 약관·개인정보·건강정보 동의 이력 저장
- 탈퇴 또는 논리 삭제 정책
- 로그인 사용자가 자기 데이터만 조회·수정하도록 권한 검증

완료 기준:

- 다른 사용자 ID를 URL이나 요청 본문에 넣어도 데이터가 노출되지 않는다.
- 비밀번호와 토큰 원문이 DB 및 로그에 저장되지 않는다.
- 만료·위조·누락 토큰이 공통 오류 형식으로 처리된다.

### 3.2 습관

- 습관 등록·조회·수정·중지·논리 삭제 API
- 반복 요일과 하루 여러 시간 설정
- 일정 변경 시 기존 이력 보존
- 오늘 또는 기간별 예정 회차 생성
- 완료·미루기·건너뛰기 처리
- 실제 행동 시각과 앱 기록 시각 분리
- 같은 회차에 대한 중복 완료 방지
- 변경 이벤트 이력 보존

완료 기준:

- 일정에서 오늘의 예정 회차가 올바르게 생성된다.
- 완료된 회차는 재알림 대상에서 제외된다.
- 과거 기록을 수정해도 원본 변경 이력을 확인할 수 있다.

### 3.3 식사와 영양

- 음식 사전 및 사용자 직접 등록 음식 API
- 식사 유형, 실제 식사 시각, 기록 상태 저장
- 한 끼에 여러 음식과 섭취량 저장
- 탄수화물·단백질·지방·당·카페인·칼로리 계산
- 섭취 당시 영양소 스냅샷 저장
- 일간·주간 영양 합계 조회
- 식사 사진 파일 키와 메타데이터 저장
- 식사 완료 이벤트를 복약 일정 계산에 전달

완료 기준:

- 음식 기준 정보가 나중에 변경되어도 과거 식사의 영양 합계가 바뀌지 않는다.
- 섭취량 변경 시 영양 합계가 일관되게 재계산된다.
- 식사 완료 시각과 앱에 기록한 시각이 구분된다.

### 3.4 의약품 사전

- 공공데이터를 내부 `medication_products` 구조로 적재
- 외부 식별코드 중복 방지
- 약 이름·성분명·업체명 기반 검색
- 페이지네이션, 정렬, 검색어 정규화
- 의약품 상세 조회
- 효능·사용법·주의사항·부작용·보관법·제형·모양 등 출처가 있는 정보 제공
- 정보 출처와 갱신 시각 관리
- 사전 항목을 개인 복약 항목으로 등록하는 API

완료 기준:

- 같은 외부 의약품이 중복 적재되지 않는다.
- 빈 검색어와 없는 검색 결과가 명확히 처리된다.
- 상세 정보에 출처와 갱신일을 표시할 수 있는 데이터가 포함된다.

### 3.5 개인 복약

- 처방약·일반의약품·영양제·운동 보충제 구분
- 의약품 사전 항목 또는 직접 입력 항목 등록
- 복용 목적, 시작일, 종료일, 회당 복용량 저장
- 요일·시간·식전·식후·공복 일정 설정
- 예정 복용 회차 생성
- 복용·건너뜀·복용하지 않음 등의 행동 기록
- 실제 복용 시각과 앱 기록 시각 분리
- 중복 복용 기록 방지
- 복용 중지와 종료 처리

완료 기준:

- 복약 일정 변경 전후의 기록이 섞이거나 사라지지 않는다.
- 같은 예정 회차에 중복 요청이 발생해도 기록이 한 번만 반영된다.
- 프론트엔드가 직접 복약 상태를 계산하지 않아도 서버 응답으로 표시할 수 있다.

### 3.6 식사 연계 복약 알림

- `식전`은 예정 식사 시각을 기준으로 계산
- `식후`는 실제 식사 완료 시각을 기준으로 계산
- 실제 식사 기록이 없을 때의 대체 정책 구현
- 식사가 늦어졌을 때 기존 알림 작업 취소 또는 재계산
- 이미 복용한 경우 알림 취소
- 재알림 간격과 최대 횟수 제한
- 알림 작업과 실제 발송 결과 분리 저장

반드시 정책으로 확정할 항목:

- 식사 기록이 없을 때 식후 약 알림을 보낼지 여부
- 식사가 예정 시각보다 크게 늦은 경우의 최대 지연 범위
- 알림 기본 간격과 최대 재알림 횟수
- 사용자가 건너뛰기를 누른 경우 당일 재알림 여부

### 3.7 통계와 분석 이벤트

- 오늘의 습관 완료율
- 일간·주간 식사 및 영양 합계
- 기간별 복약 이행률
- 화면 조회, 등록 시작, 등록 완료, 오류, 재시도 이벤트 수신
- 알림 발송·도착·열람·행동 완료 사이의 시간 계산이 가능한 키 설계
- 이벤트 발생 시각과 서버 수신 시각 분리
- 민감정보 원문을 분석 속성에 넣지 않도록 검증

## 4. 현서에게 제공할 항목

각 기능 착수 전에 다음 자료를 제공한다.

1. 엔드포인트 목록
2. 요청 JSON 예시
3. 성공 응답 JSON 예시
4. 필드 오류와 공통 오류 예시
5. 허용 상태값 목록
6. 날짜와 시간 예시
7. Mock 응답 파일
8. 테스트 계정과 개발 서버 주소
9. 변경 내역과 적용일

API가 아직 완성되지 않았더라도 계약을 먼저 제공하여 B가 Mock 데이터로 작업할 수 있게 한다.

## 6. 매일 확인할 체크리스트

- 오늘 추가한 API가 계약 문서와 일치하는가?
- 인증 없이 보호 데이터에 접근할 수 없는가?
- 다른 사용자의 데이터를 조회할 수 없는가?
- 중복 요청에도 데이터가 한 번만 생성되는가?
- 시간대 변환이 정확한가?
- 로그에 토큰이나 건강정보 원문이 남지 않는가?
- 현서가 사용할 Mock 또는 실제 응답이 준비되었는가?
- 테스트가 자동으로 실행되는가?

## 7. 성준이 하지 말아야 할 일

- 화면을 완벽하게 다듬느라 백엔드 핵심 일정을 늦추지 않는다.
- 2개월 MVP 제외 기능을 DB에 있다는 이유로 모두 구현하지 않는다.
- API 응답을 프론트엔드와 상의 없이 자주 변경하지 않는다.
- 의료 판단을 자체 규칙으로 단정하거나 출처 없는 경고를 생성하지 않는다.
- 시연 직전에 DB 구조를 대규모로 변경하지 않는다.
- 현서가 만든 AI 코드를 검토 없이 핵심 브랜치에 합치지 않는다.

## 8. 최종 인수 조건

- 서버 실행 방법과 환경변수 목록이 문서화되어 있다.
- 빈 MariaDB에서 마이그레이션으로 스키마를 재현할 수 있다.
- 시연 계정과 Seed 데이터 생성 방법이 있다.
- OpenAPI 문서가 실제 구현과 일치한다.
- 핵심 시나리오 통합 테스트가 통과한다.
- 장애·오류 발생 시 확인할 로그 위치와 복구 절차가 있다.
