# 고정시간 복약 회차 자동 생성 — 1차

2026-10-19. 서버 내부 작업이며 새 공개 API·DB 마이그레이션은 없습니다. 기존 V1~V10·18개 실행용 테이블을 사용합니다.

## 실행 설정

- 기본값은 비활성화입니다. 서버 환경변수 `MEDICATION_GENERATION_ENABLED=true` 또는 `medication-generation.enabled=true` 설정 후 재시작하면 활성화됩니다.
- 시작 30초 후 첫 실행, 배치 종료 60초 후 다음 실행. 외부 예약 서비스나 푸시 공급자는 호출하지 않습니다.
- 한 배치 최대 50개 개인 복약 항목을 ID 키셋 순서로 조회합니다. 후보는 ACTIVE 개인 복약·ACTIVE 계정·일정 존재 조건입니다. 조회 후보에는 ID만 포함하며 이름·메모·건강정보를 작업 로그에 쓰지 않습니다.
- 각 항목은 별도 트랜잭션에서 사용자를 잠그고 활성 상태·소유권·필수 동의를 다시 확인합니다. 중지·탈퇴·동의 철회와 경쟁해도 잠금 획득 뒤의 상태를 적용합니다.
- 각 일정 시간대의 **오늘 하루**만 생성합니다. 요일, 개인 복약 시작/종료일, 일정 버전 유효기간, 하루 슬롯을 기존 수동 생성과 동일하게 적용합니다.
- 날짜가 바뀌면 다음 순회에서 새 날짜를 처리합니다. 프로필이나 서버 시간대가 아닌 일정에 저장된 시간대를 사용합니다.

## 중복·실패·복구

- 기존 POST 생성과 동일한 사용자 잠금 및 일정ID/날짜/슬롯 UNIQUE를 사용합니다. 동시에 자동·수동 요청이 들어와도 중복 회차를 만들지 않습니다.
- 이미 존재하는 TAKEN/SKIPPED/NO_STOCK/CANCELLED를 다시 SCHEDULED로 되돌리거나 삭제하지 않습니다. 실제 복용 기록도 변경하지 않습니다.
- 한 항목의 실패는 다른 항목을 롤백하지 않습니다. 업무 조건 거절은 rejected, 예상하지 못한 처리 오류는 failed 수로만 로그에 남깁니다. 예외 원문·SQL·사용자ID·약 이름·메모는 출력하지 않습니다.
- 대상 조회 자체가 실패하면 현재 커서를 유지하고 다음 실행에서 재시도합니다. 개별 항목 실패는 다음 전체 순회에서 재시도합니다.
- 마지막 배치 후 커서를 처음으로 되돌립니다. 이미 지난 ID 위치에 새 항목이 추가되면 다음 순회에서 처리됩니다. 재시작 시 커서는 초기화되지만 DB 중복 검사로 기존 회차는 보존됩니다.
- DST 누락/중복 시각은 기존 정책대로 거절하며 해당 약의 오늘 생성 트랜잭션 전체를 롤백합니다. 임의로 시간을 이동하거나 복용량을 변경하지 않습니다.

## 시연 순서

1. 격리된 개발 DB에서 서버 자동 생성 설정을 활성화합니다. 운영 설정을 임의로 켜지 않습니다.
2. 현재 동의를 가진 계정으로 개인 복약과 오늘부터 유효한 고정시간 일정을 등록합니다.
3. 다음 해당 항목 처리 후 `GET /api/v1/medication-occurrences?date=YYYY-MM-DD`로 조회합니다. GET 자체는 쓰기를 수행하지 않습니다.
4. `POST /api/v1/medication-occurrences/{id}/actions`로 행동을 기록합니다.
5. 이후 자동 배치 또는 동일 날짜 수동 생성 요청을 반복해도 같은 회차 ID·최종 상태가 유지됩니다.

## 범위·주의사항

- 새 일정 저장 직후 즉시 생성은 아닙니다. 대상 N개를 모두 확인하는 데 대략 `ceil(N/50)`회의 배치와 각 처리 시간이 필요합니다. 1분 내 전체 사용자 갱신을 보장하지 않습니다.
- 미래일 선생성·전일 이전 장애 기간 소급 생성은 하지 않습니다. 서버가 늦게 켜져도 오늘의 지나간 예정 시각은 예정 회차로 저장하지만 실제 복용/미복용을 추정하지 않습니다.
- 과거 회차 누락 복구 정책, 정밀 알림 발송 시각, 분산 작업 분배·운영 지표/경보는 후속입니다. 여러 인스턴스에서 실행하면 동일 항목을 반복 확인할 수 있으므로 1차 운영은 한 작업 인스턴스에서만 활성화하세요.
- 기존 일정 이력 전체 조회의 한계는 남아 있습니다. 50개는 배치 후보 개수 제한이며 전체 SQL 비용·사용자별 잠금 대기 시간을 보장하는 상한은 아닙니다.
- 실제 푸시 알림·재알림, 식사 연계 계산, 복용 기록 정정, 재고 차감, Android E2E는 이번 범위가 아닙니다.
- 테스트는 작업 메서드 직접 호출, 스케줄 등록 조건, H2/MariaDB 기록·중복·트랜잭션 경계를 확인합니다. 실제 서버에서 24시간 날짜 전환이나 운영 장기 스케줄링을 관찰한 결과는 아닙니다.

근거: `MedicationGenerationJob`, `MedicationGenerationScheduler`, `MedicationScheduleService.generateToday`, `MedicationGenerationIntegrationTest`, `MedicationGenerationJobTest`.
